# Tumoflip Dev 009-038 — Hormann HSM and KeeLoq timing

Development build for testing on owned/authorized devices, not a Stable
promotion. F7 API stays **88.23**; keep the full **4096-byte physical C2 reserve**.

## Changes since 009-037

- **Hormann HSM:** recognize both seven- and eight-one preambles. All seven
  common preamble bits and both stop bits remain mandatory; require exactly
  44 bits and reject overlong frames before the bit counter can wrap.
- **KeeLoq TE200:** recognize the faster timing in addition to the existing
  400 us path. Use preamble and sync together so the overlapping sync bands
  do not steal a nominal 400 us capture. Scale timing tolerances with the
  measured fast TE, retaining oscillator drift support.
- Save nominal `TE: 200` for a fast capture and use that timing when loading
  it for ordinary supported playback. Standard captures keep their existing
  file layout. Missing, invalid or unsupported TE falls back to 400 us on
  each load, without inheriting the previous file's speed.
- Bound KeeLoq frames to 64..66 bits. Keep existing seeds, manufacturer-name
  migration, counter modes, custom buttons and KEY/new-Monarch receive-only
  restrictions. No new key generation or counter-resync mode is added.
- Share private Seed/Manufacture/TE/CounterMode parsing between load paths;
  failed rewinds/read outputs cannot be mistaken for successful metadata.
  Compact identical waveform and button logic preserves the flash reserve
  without removing functionality or adding public API symbols.

All 009-037 changes remain, including external Core-group Freezer, Marantec24,
Linear Delta3, Holtek, CAME TWEE and truthful diagnostic reports. Previous GUI/IR,
Honda hopping and user-data preservation checks remain in the regression suite.
No new T5577 password/dictionary workflow, TM01x writing, Remote Analyzer,
JavaScript/GPS export, public decoder-structure change or SD cleanup is included.

## Installation / compatibility

1. Back up `/int`, important SD files, recordings and application data.
2. In TumoCompanion refresh **Firmware → Dev** and install **009-038 with
   matching native resources** using the normal update flow.
3. Keep **FW Packages Dev031** and **TumoCompanion 1.11.33**. These fixes live
   in existing shared resident protocol implementations and require no new
   independent package revision, package reinstall, iOS or ESP32 image.
4. No factory reset, SD cleanup, BLE re-pairing or diagnostic-firmware flash
   is required. Published Stable/earlier Dev files and catalog history stay
   unchanged.

No public API breaking change is introduced. A fast KeeLoq capture carries an
optional TE field that older builds do not implement; do not expect TE200
playback timing to survive a downgrade to an older firmware. Keep the original
capture/RAW file and use a compatible build when testing it.

## Validation / device acceptance

Implementation [PR582](https://github.com/squazaryu/tumoflip/pull/582) passed
1340 full host tests, 270 actual FAP/FAL metadata cases, 43 public-only protocol
import contracts, normal/diagnostic CI and CodeQL. Named production C bodies
have 93.33% measured source-region coverage with fatal ASan/UBSan. All
16,777,216 original/direction/fallback button mappings match the frozen 009-037
implementation. These are software checks, not physical receiver acceptance.

Publication additionally requires exact merged-version build/tests, updater
DfuSe/C2/resource/SDK/archive checks and downloaded-byte verification.

After installing, test on owned devices or copied captures:

- Confirm device identity **009-038 / API 88.23**.
- Check own HSM captures with both supported preambles, if available.
- Check a TE200 capture through receive, save, reopen and ordinary supported
  playback. Verify an older 400 us file still works after opening the fast one.
- Recheck existing custom buttons and saved metadata without altering originals.
- Confirm other Core/explicit protocol packs load and recordings/settings remain.

Fresh independent review and hardware/RF acceptance have not been performed.
No device was flashed by this release preparation. This is not a claim that
historic idle-OOM or Bluetooth-channel symptoms are fixed.

# Upstream 1132/1133 adaptation

Dev 008-021 contains two narrow, API-compatible adaptations from Unleashed.

## Power initialization (#1132)

`furi_hal_power_init()` already records the result of each retry loop in the
latched `gauge_ok` and `charger_ok` fields. The final log now reports `Init OK`
only when both succeeded; otherwise it emits `Init failed: gauge %u, charger %u`
with the actual flags. This is diagnostic only: retry counts, timing, battery
state handling and the power drivers are unchanged.

## Plugin directory scanning (#1133)

Tumoflip already had the upstream prefix-filter concept under the stable public
name `plugin_manager_load_all_with_prefix()` and already filters Sub-GHz radio
drivers by `radio_device_`. This adaptation keeps that API and adds the missing
failure semantics:

- a bad plugin is freed and the scan continues, so later valid drivers are still
  registered;
- an application-ID mismatch encountered during a directory scan is ignored as
  an expected shared-directory entry, while a direct single-file load still
  reports it;
- the first real load error is returned after the scan;
- a normal end-of-directory (`FSE_NOT_EXIST`) is distinct from a failed read and
  failed reads return `PluginManagerErrorLoaderError`;
- a zero-driver scan is visible through a warning, while a partial scan still
  exposes every successfully loaded driver.

Example plugin hosts now log a partial scan and free their manager on the normal
exit path instead of returning before cleanup. No new exported API symbol is
introduced, so API remains 88.5 and existing FAPs do not need a rebuild solely
for the loader interface.

The separate Unleashed #1134 Add Manually extraction is intentionally not part of
this release; our existing manual generators and their product-specific behavior
remain resident.

## Verification boundary

Focused source contracts, Sub-GHz protocol-pack tests, loader tests, and the full
Python regression suite run before publication. The firmware build and APPCHK
must pass. Device acceptance should still include a boot with healthy power,
Sub-GHz startup with a valid external CC1101 driver, and a scan containing a
stale/bad `.fal` before a valid driver; logs should report the partial error but
the driver must remain available. This cannot be simulated by host tests alone.
